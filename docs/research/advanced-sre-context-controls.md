# Azure SRE Agent context controls and token observability

Research for [Establish SRE Agent context controls and token observability](https://github.com/JoranBergfeld/sre-agent-workshop/issues/75), supporting [the advanced scenario map](https://github.com/JoranBergfeld/sre-agent-workshop/issues/70).

**Checked:** 2026-10-28. **Scope:** documented Azure SRE Agent capabilities, not a deployed-tenant acceptance test. No infrastructure, experiment, or final scenario design is implemented or selected here. Only public first-party product material and the author's explicitly illustrative demo were consulted; no private repository code was sent to external research services.

## Findings in brief

- **Customization is feasible:** custom-agent instructions, skill procedures, knowledge retrieval, selected tools, bounded queries, connectors, and conversation compaction are documented controls. These are not synonymous with coding-agent instruction files. [S1–S8]
- **Real input/output counters exist:** Application Insights `ModelGeneration` events document `InputTokens`, `OutputTokens`, `ModelId`, `AgentName`, and `ThreadId`. The portal's consumption page separately exposes per-thread AAUs and CSV export. Do not settle for character estimates when these counters are available. [S9–S10]
- **Exact context occupancy is not established:** the audited sources do not expose a documented occupancy percentage, model-window limit for the active request, or complete prompt-component ledger. Per-call prompt tokens are observable, but not a window-utilization meter. [S3, S9, S17]
- **SRE custom agents are not isolated coding subagents:** they receive full conversation history and share the accumulating thread context. A handoff is not evidence that raw context has been removed. [S1]
- **Cache billing is documented; cache counters are not:** input, output, cache-read, and cache-write tokens determine active AAUs, but the documented audit schema exposes only input/output counters. AAUs cannot uniquely recover the four quantities. [S9–S11]
- A baseline/tuned comparison can examine total observed model usage, AAUs, tool-output proxies, and evidence quality, **without promising savings or degradation**. Persistent learning, automatic compaction, provider routing, and background work complicate attribution and repeatability. [S3–S4, S9–S11, S17]

## Vocabulary and product boundary

For this research, **working context** means information supplied to a model invocation; **context occupancy** means its use relative to that invocation's effective capacity; **cumulative usage** sums consumption over invocations, including repeated context. **Persistent knowledge** survives threads but is not necessarily loaded wholesale into each request. **AAUs** are Azure billing units, not tokens or currency. **Handoff** must specify whether it means an SRE specialist switch in one thread or a GitHub issue delivered to a different product. These distinctions follow the separate thread, memory, audit, and billing surfaces. [S1, S3–S4, S9–S11]

Azure SRE Agent investigates operational resources and has its own Builder, skills, knowledge, connectors, and runtime policies. GitHub Copilot cloud agent is a separate repository-development service capable of editing files and running tests in an ephemeral development environment. Copilot repository instructions, custom agents, hooks, session logs, and product billing must not be presented as automatically available in SRE Agent merely because the names overlap. GitHub documentation describes conversation sharing within Copilot Chat/cloud-agent sessions; it does not establish automatic sharing of an Azure SRE Agent thread. [S1–S2, S12, S22]

Free-form instructions are guidance, not a hard runtime quota. A row limit alone does not bound a very wide/long row. Predefined query parameters must also be constrained if a hard bound is needed. |
| Large-output processing | Product engineering describes storing large results in sandbox files, then inspecting/filtering/analyzing them before returning summaries; Code Interpreter/workspace tools provide computation. [S15, S18] | Useful first-party architectural evidence, **not** a documented user setting for universal output paging or a known interception threshold. Do not promise every tool result bypasses the model. Python-tool fresh containers are not a persistent cross-call filesystem. [S14] |
| Hooks / output governance | Builder → Hooks or per-custom-agent hooks; `Stop` and successful `PostToolUse` events; command or LLM evaluation, blocking, and additional context. [S16] | Hooks are not a documented arbitrary rewrite/truncation API for tool results. PostToolUse is after execution, not a pre-execution safety guarantee. Prompt hooks add model work; injected context adds context. Administrators control hooks. [S12, S16] |

[S1] | **Single shared conversation** containing messages, tool calls and results. Not a clean slate or a summary-only child result. [S3] | No documented trigger threshold, compression ratio, exact retained set, or occupancy meter. Summary fidelity still needs checking. Thread deletion is not documented as deleting previously extracted memories or resetting cache. |
| Cross-session history | Automatic learning about 30 minutes after inactivity/completion, same-resource priority, saved memories, persistent knowledge; `#remember`, `#retrieve`, `#forget`. [S4] | A new thread is not a cold agent. `#forget` removes a saved memory, not a documented universal wipe of learned state. No established single control to disable/reset every learning source for a clean experiment. |
| Handover to GitHub | Code Access for source context; GitHub Connector/MCP for issue operations, including issue title/body/labels/assignees. [S19] | A bounded issue can carry evidence references, exact resource/commit identifiers, time window, hypothesis, reproduction and acceptance checks. This is feasible packaging, not automatic transfer of the full SRE runtime context. GitHub permissions, Copilot access and its separate usage must be verified independently. [S19, S22] |

### Permissions and safety are separate from prompt optimization

The current role reference distinguishes SRE Agent **Standard User** (chat, knowledge uploads, repository connectors), **Author** (custom agents and response plans, but not chat or portal knowledge upload), and **Administrator** (settings/approvals/administration). A learner who needs to author and chat needs Standard User + Author or Administrator. Azure Owner/Contributor alone do not grant the required SRE data actions; the usage page separately says consumption visibility requires Contributor/Owner. Preflight both SRE access and Azure access to consumption/telemetry instead of assuming one role covers everything. [S10, S12]

Agent permissions are another layer: the agent managed identity needs access to monitored data; ADX Kusto tools document `AllDatabasesViewer`; Application Insights querying needs the appropriate Azure monitoring access. Reader-level agent setup still documents Monitoring Contributor at subscription scope and possible on-behalf-of elevation. “Reader mode” must not be treated as a blanket no-write guarantee. [S13, S20]

Tool selection, access policies, run modes and hooks serve different purposes. Policies document global allow/ask/deny and allow-only narrower scopes; a user-defined hook allow can override even global deny. Review mode alone therefore does not prove every write requires approval. A context exercise need not enable write operations; least privilege and actual runtime policies remain necessary independently of instructions. [S16, S21]

## Measurement and accounting evidence matrix

| Quantity | Classification | Exposed evidence / limit |
| --- | --- | --- |
| Current context occupancy, remaining capacity, percentage full | **Not established as exposed** | No documented SRE field/UI counter in checked thread, reasoning, audit or usage references. The active model's advertised maximum elsewhere would not establish this harness's available capacity. [S3, S9–S10, S17] |
| Input tokens per completed LLM call | **Directly documented measurement** | Application Insights `customEvents`, `name == "ModelGeneration"`, `EventType == "ModelGenerationEnd"`, `InputTokens`. Include model, agent, thread and time dimensions. This is prompt usage, not a component-by-component window ledger. [S9] |
| Output tokens per completed LLM call | **Directly documented measurement** | Same event's `OutputTokens`. Billing describes output as including responses/reasoning; the audit reference does not define a separate visible/hidden-reasoning breakdown. UI response length is not equivalent. [S9, S11] |
| Cumulative input/output | **Derived from direct measurements** | Sum completed-call counters over the declared run boundary, across **all** `AgentName` and `ModelId` values. Repeated context counts repeatedly. Do not add starts and ends, assume failed calls are free, or replace missing counters with zero. [S9, S11] |
| Cache-read / cache-write tokens | **Metered internally; customer counters unverified** | Pricing defines separate types/rates. The published `ModelGeneration` field list and consumption CSV do not document cache fields or cache hits. Inspect actual supported telemetry during preflight; absence here is not a claim that no richer tenant schema exists. [S9–S11] |
| Delegated specialist usage | **Documented attribution, conditional completeness** | `AgentName` identifies the LLM caller; `SubAgentName` identifies tool callers; `AgentHandoff`, `TraceId`, `ParentSpanId` and `ThreadId` support correlation. Shared-thread specialist calls must be included, not just `meta_agent`. [S1, S9] |
| Hook/evaluation/background work | **Accounting boundary requiring validation** | Active billing includes background operations and hooks can invoke their own models; the audit schema does not explicitly guarantee that every such category appears under the initiating thread. Check related traces/threads and disclose unexplained coverage. [S9, S11, S16] |
| Per-thread active AAUs | **Directly documented billing-unit observation** | Settings → Agent consumption table and CSV: thread title, type, AAUs, status, last-active date and ID. History covers six months. This is a weighted billable unit, not raw token count. [S10] |
| Exact active cost reconstructed from audit input/output | **Unavailable from those fields alone** | Four token classes and per-model rates determine AAUs. Cache split/semantics and potentially missing categories prevent exact reconstruction from only input/output totals. One AAU total is one equation with multiple unknown quantities. [S9, S11] |
| Money | **Measured invoice/Cost Management; otherwise estimate** | Use Azure Cost Management for billing and the subscription's actual currency/offer/rate. Per-thread AAUs × verified unit price is an attributed active-cost estimate, not the complete invoice. Public pricing rendered `$-`, so this research establishes no dollar-per-AAU quote. [S11, S23] |
| Fixed and other service costs | **Separately account** | Always-on: 4 AAUs per agent-hour until deletion, except eligible evaluation waiver. Monitor ingestion/querying, infrastructure, integrations and egress can add costs. Stop does not eliminate always-on billing. [S11, S24, S26] |
| Tool-output size, query rows, tool calls, elapsed time, retries, compaction count | **Observable proxies where recorded** | Audit ToolStart/ToolEnd fields include inputs/outputs and call IDs; Playground query tests show rows/columns/time. Characters/bytes and row counts measure payload, not model tokens or retained occupancy. ToolOutput may be truncated by telemetry limits or altered by the harness. [S8–S9, S15] |
| Approximate tokens in visible text | **Estimate only** | A declared external tokenizer/version can estimate a captured artifact; hidden prompts, schemas, retrieval, serialization, images, reasoning, cache treatment and summaries remain outside it. Do not label estimates as SRE counters. [S2–S4, S9, S11] |
| Quality or context “rot” | **Outcome evaluation, not token measurement** | Correct diagnosis, retained evidence, uncertainty, safe recovery and handover completeness can be scored against known incident facts. Playground AI scores are supportive assessments, not proof of diagnosis correctness or a causal degradation threshold. [S8, S15] |
| GitHub coding-agent work | **Separate product ledger** | GitHub plan/policy/session access and billing apply independently. An Azure AAU/thread export does not establish downstream Copilot usage. If raw downstream/delegated counters cannot be obtained, report the gap rather than claim end-to-end token savings. [S19, S22] |

The published rates at retrieval, in **AAUs per million tokens**, are: Claude Opus 4.6 input/output/cache-read/cache-write **100/500/10/125**; GPT 5.3 Codex and GPT 5.2 **35/280/3.5/0**. Treat these as dated tariff evidence, not a guarantee of which model will run. The provider-selection reference says the user selects a provider and the service routes models per task; record actual `ModelId` values. The billing example's approximately 200K input for an investigation is cumulative illustrative usage, **not** a declared 200K context window. [S9, S11, S17]

## Feasibility of a baseline-versus-tuned comparison

**Feasible as an empirical comparison; not yet demonstrated in a tenant.** Several supported interventions could be compared: focused instructions, concise on-demand skill/knowledge material, explicit resource/time/column/result bounds, a preconfigured telemetry connector, external computation, or deliberate compaction. These are candidate dimensions, not a selected experiment. Changing all at once tests a package, not the causal contribution of each control. [S1–S8, S13–S18]

A defensible comparison would need:

1. **A controlled incident and retained evidence.** Same injected failure, resource topology, application version, telemetry interval/data and correctness rubric. A noisy baseline must still contain the necessary evidence; a tuned run must not merely hide contradictory logs or receive the answer.
2. **Recorded treatment and runtime.** Preserve the actual prompt/instruction, skill/knowledge versions, effective tool selection and overrides, connector configuration, permission/run-mode settings, provider, observed model IDs, compaction and thread IDs. Do not assume fixed routing. [S5, S17, S21]
3. **Explicit isolation limits.** Use distinct threads; `/clear` does not reset learned state. Record pre-existing knowledge, same-resource memories, automatic learning/background tasks, cache warmness if observable, and run order. Separate fresh agents or counterbalanced/repeated runs are possible mitigations with additional setup/cost, not a proven complete reset procedure. [S3–S4, S11]
4. **An accounting preflight before promising a token exercise.** Confirm ModelGenerationEnd events arrive with numeric nonempty counters, usable thread/trace attribution, actual model IDs, tool results and exportable thread AAUs. Check sampling, retention, truncation, ingestion delay, duplicate records and errors against observed calls; these completeness properties were not validated here. Include all specialists and attributable hooks/evaluations; separately enumerate async or unmatched activity. [S9–S11, S16]
5. **A layered ledger.** Report direct input/output measurements; observed AAUs; cache quantities as unavailable unless independently verified; visible payload/turn/call/latency proxies; and any tokenizer estimates separately. Reconcile thread totals with the applicable agent/time interval without charging the same work twice. Keep always-on allocation and downstream GitHub usage distinct. [S9–S11, S22]
6. **Independent success checks and honest interpretation.** Compare diagnostic correctness, citations and retained evidence, safe proposed recovery, and a complete bounded handover, not merely shorter output or lower AAUs. Report variation and counterexamples. A compacted run might lose details; a longer grounded run might be better; a smaller visible payload may cost more in retries, hook evaluation or output reasoning. None is a guaranteed result. [S8, S11, S15–S16]

**Fallback:** if telemetry is missing, a payload/turn/elapsed-time plus available-AAU comparison remains possible, explicitly labeled proxy-based. It does **not** meet a promise of measured raw token accounting. If downstream usage is unavailable, the result must be scoped to SRE investigation rather than advertised as total agent-system efficiency.

## What transfers from the author's context-window demo?

The [demo](https://whoami.joranbergfeld.com/demos/context-window) calls itself a modeled representative coding session, not a recording. Its 200,000-token capacity, 154,400-token occupancy, schema/instruction allocations, repeated-input assumptions and delegated-token ledger are pedagogical examples, not SRE product measurements.

| Demo idea | Azure SRE Agent evidence / nontransferable assumption |
| --- | --- |
| Persistent instructions consume context | Custom instructions, skill descriptions and synthesized knowledge provide real analogues; exact allocations and replay behavior are not exposed as that ledger. [S1–S2, S4] |
| Every MCP schema is permanently loaded | SRE documents scoped tool selection, platform/published-list filtering and skills that load/unload. No verified “all schemas on every turn” guarantee. [S2, S5, S18] |
| Retrieved output permanently stays in the window | Automatic/manual compaction and the engineering team's file-mediated large-output processing contradict an unconditional permanent-growth model. Exact routing/retention varies and is not quantified here. [S3, S15] |
| Subagents return a short summary instead of their raw context | **Does not transfer to documented SRE custom-agent handoffs**, which share full thread context. [S1] |
| Subagents are the only way to give context back | Not applicable: SRE documents compaction, fresh threads, active-skill unloading and external analysis. These have different persistence/fidelity trade-offs. [S2–S4, S15] |
| Smaller parent window means cheaper work | Not established; total model work includes specialists, cache classes and background activity, and downstream Copilot has a separate ledger. [S9–S11, S22] |
| A threshold predicts quality degradation | No universal SRE threshold or guaranteed baseline failure is documented. The engineering blog reports historical observations, not a workshop service contract. [S15] |

## Availability, dates, licensing and unresolved discrepancies

- **GA, not merely preview:** Microsoft's product-team GA announcement was published **2026-03-10** (modified 2026-04-10). Do not carry forward the 2025 preview classification. GA does not prove each optional capability is GA: workspace file/terminal tooling is explicitly behind **Experimental Settings** in the July reasoning reference. Other capability pages cited here do not individually establish a separate GA/preview lifecycle commitment. [S18, S25]
- **Subscription/region gates:** the supported-regions reference (updated **2026-09-18**) lists 22 regions, including Sweden Central, UK South, East US 2 and Australia East. Actual availability is subscription-dependent; an empty region picker can require registration. The older FAQ lists only three regions. Prefer the dedicated current region reference and tenant picker over that older summary. Provider availability also depends on region/subscription. [S17, S24, S26–S27]
- **Commercial prerequisite:** Azure subscription and SRE service consumption apply; this is not unlocked just by a GitHub Copilot license. GitHub access for the handover and cloud-agent execution has its own plan/organization-policy requirements. The inspected sources do not establish an additional SRE per-seat Copilot prerequisite. [S22, S24]
- **Billing changed:** the product-team announcement dated **2026-04-02**, effective **2026-04-15**, replaces active-flow seconds with token-based metering. The product marketing page still says 0.25 AAUs/second; do not use that stale figure for this experiment. Current pricing/billing documentation and the dedicated pricing page describe token-based active flow. [S11, S23, S28–S29]
- **Trial discrepancy:** the evaluation reference (updated **2026-09-25**) offers new customers up to three agents for up to 30 days with always-on charges waived, while active use remains paid. The pricing-page FAQ still says free/trial/Dev-Test AAUs are unavailable. These can reflect different meanings of “trial AAUs,” but entitlement should be verified in the create flow/account terms; promise neither free active usage nor universal trial eligibility. [S23–S24]
- **Knowledge-limit discrepancy:** the March custom-agent article says Markdown/text, 50 MB/file, 1,000 files per custom-agent instance. The dedicated upload reference (updated **2026-06-06**) distinguishes chat attachments (10 MB/file, five files/50 MB per message), knowledge uploads (16 MB/file, 100 MB per upload), and agent-generated Markdown/text (16 MB/file). Prefer small Markdown assets and the dedicated surface-specific reference, then verify the actual portal; do not silently combine these limits. Agent-generated upload documents require version 26.1.57.0 or later. [S1, S6]
- **Data boundaries:** provider choice matters: the provider reference says Azure OpenAI is covered by EU Data Boundary commitments and Anthropic is excluded. Source, tools and telemetry may contain sensitive operational data; use synthetic/redacted workshop assets and restrict log access. This research did not validate tenant residency settings or telemetry export policies. [S9, S17]
- **Historical architecture versus configurable contract:** the December engineering article (modified **2026-01-11**) describes file-mediated output management and compaction, and describes tool-call chaining as future work. Its performance numbers and handoff-failure observations are historical engineering evidence, not current guaranteed limits or proof that a learner can toggle those internals. [S15]

### Implications for the next decisions—not final design choices

The next design decision can safely consider **observable customization plus per-call input/output and per-thread AAU accounting**, conditional on a tenant telemetry check. It cannot safely require a live percentage-full visualization, isolated SRE specialist windows, exact cache/delegated end-to-end totals without validation, or a predetermined “context rot” failure.

Still to decide elsewhere: which customization dimension to teach, acceptable missing-metric fallback, reset/order protocol, independent correctness rubric, privacy-safe handover payload, and whether the learning objective requires downstream Copilot accounting. No language, security-tool choice, final experiment, or scenario implementation is selected by this ticket.
